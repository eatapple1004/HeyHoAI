# [개발자 보고] 이미지·영상 저장 현황 및 남은 작업 (2026-07-06)

## TL;DR
- 신규 이미지/영상은 여전히 **서버 로컬 `process.cwd()/tmp/images`(비영속)** 에만 저장됨 → 재배포·재시작·메모리킬 시 파일 소실 → 라이브 **간헐 404**(릴스가 대표적으로 빈 박스로 뜸).
- 이번에 **오브젝트 스토리지(S3/R2) 이중화 코드**를 넣고 **prod 배포 완료**(`upstream/main = 037fcae`).
- **단, 아직 스위치 OFF 상태.** `MEDIA_S3_BUCKET` env 미설정이라 코드는 **현행 로컬 동작 그대로** = **404는 아직 안 고쳐짐.** 버킷 provisioning + env 넣어야 실제 발동.
- 이미 사라진 파일은 복구 불가(재생성 필요). 스토리지는 "앞으로" 안 사라지게 하는 것.

---

## 1. 현재 저장 구조
- 저장: 모든 생성물(이미지/영상/BGM 병합 릴)을 `process.cwd()/tmp/images/<uuid>.<ext>` 에 `fs.writeFileSync`.
- 서빙: `app.use('/images', express.static(tmp/images))` (이번 변경 전). DB엔 `file_path='tmp/images/<file>'`, 프런트는 `/images/<basename>`로 참조.
- 배포: 단일 EC2(13.209.72.131) + pm2 `instances:1`(fork) + nginx→127.0.0.1:3000. `tmp/`는 `.gitignore`(untracked).

## 2. 404 근본원인 (단일 인스턴스·영속 EBS 전제에서 후보 3)
1. **재배포 시 tmp 소실** — `git clean -fdx`·재클론·"public 통째 재배포" 같은 스텝이 끼면 untracked `tmp/images` 전멸. (순수 `git pull`이면 안 지워짐.)
2. **pm2 메모리킬** — `max_memory_restart:'500M'`. 영상 finalize가 전체 영상+오디오를 메모리 Buffer로 다뤄, 큰 영상에서 500M 초과 시 finalize 도중 재시작 → 반쯤 쓰인 파일 = 404.
3. **cwd 드리프트** — `process.cwd()` 기준이라 pm2 실행 위치가 바뀌면 저장 디렉터리 자체가 갈림.

→ **원인 확정용 진단(읽기 전용, 배포된 에러라벨 활용)**:
```sql
-- 실패/원인 분포 (finalize 단계 라벨은 c9d8be3에 포함되어 이미 배포됨)
SELECT error, count(*) FROM video_jobs
WHERE status='failed' AND created_at > now() - interval '3 days'
GROUP BY 1 ORDER BY 2 DESC;
```
```bash
# succeeded인데 파일 없으면 = tmp가 쓸림(원인 1 확정)
ls -la ~/HeyHoAI/tmp/images/*.mp4 | wc -l
```
`error`에 `file write failed (FS EROFS/EACCES ...)` 류가 뜨면 FS/디스크, 안 뜨고 파일만 없으면 배포 클린이 유력.

## 3. 이번 배포에 포함된 것 (`037fcae`, prod 반영 완료)
**핵심**: `MEDIA_S3_BUCKET` 미설정 시 **동작 0 변경**(env-gate). 그래서 지금 배포돼도 현행과 동일하게 안전.
- **신규 `src/storage/mediaStore.js`** — S3 호환 어댑터(**AWS S3·Cloudflare R2 공용**, `@aws-sdk/client-s3` lazy-require). `isRemote()`·`put`·`putFile`·`remoteUrl`·`getObject(Range)`.
- **`src/index.js` `/images/:file`** — 로컬 파일 우선(과거 파일·Range 지원=영상 seek) → 로컬 없으면 원격 폴백 → 404.
  - `MEDIA_S3_PUBLIC_BASE` 있으면 **302 redirect(공개 CDN/버킷)**, 없으면 **앱 프록시 스트리밍(비공개 버킷, Range→206)**.
- **dual-write 훅**(로컬 write 유지 + best-effort 업로드, 실패해도 throw 안 함): `generate.route`(스튜디오 img/vid)·`videoJob.service`(잡 영상 finalize)·`nanoBanana.provider`·`account.route`(발행 img/vid)·`adminRefine`·`scheduler`(BGM 병합 릴).
- `src/config/index.js` — `MEDIA_S3_*` env 5종(전부 optional/default). 프런트·DB **0 수정**.
- ⚠️ 배포 시 **`npm install` 필요**(신규 `@aws-sdk/client-s3` 의존성). 이미 반영됨.

## 5. 실제 해결에 필요한 작업 (개발자 협업)
1. **버킷 provisioning** — 대표 결정은 **Cloudflare R2**(6/24). R2 버킷 생성(예 `doppia-media`) + API 토큰(Put/Get, 해당 버킷 스코프).
2. **prod `.env`**:
   ```
   MEDIA_S3_BUCKET=doppia-media
   MEDIA_S3_ENDPOINT=https://<account_id>.r2.cloudflarestorage.com
   AWS_ACCESS_KEY_ID=<R2 토큰 id>
   AWS_SECRET_ACCESS_KEY=<R2 토큰 secret>
   # 공개 CDN 방식이면 추가: MEDIA_S3_PUBLIC_BASE=https://<공개 도메인>
   ```
3. `pm2 restart heyhoai` → 새 생성물부터 R2에도 저장.
4. 검증: 영상 1건 생성 → 로그 `[MediaStore] uploaded ...` 확인 → `tmp/images`의 그 파일 삭제해도 `/images/<file>` 정상 재생.
5. (선택) 과거 파일 백필: 로컬에 남은 `tmp/images/*`를 일회성 `aws s3 sync`(R2 엔드포인트).

## 6. 결정 필요 — 서빙 방식 (비용/성능 트레이드오프)
- **비공개 프록시**(6/24 결정, `PUBLIC_BASE` 미설정): 동일출처·버킷 비공개. 단 모든 미디어가 EC2 경유 → EC2 대역폭 부하 + **AWS egress 과금**(R2 무료 egress 못 누림)·엣지 캐시 없음.
- **공개 CDN 302**(`PUBLIC_BASE` 설정): R2가 직접 서빙 → **egress 무료 + CDN 캐시 + EC2 부하 0**. 오브젝트 공개(어차피 Community에 공개되는 콘텐츠).
- 코드는 **둘 다 지원**, env로만 전환. 트래픽·비용 관점에선 공개 CDN 권장(대표와 재확인 필요).
