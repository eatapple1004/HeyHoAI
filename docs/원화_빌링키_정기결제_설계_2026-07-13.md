## 0. 한 줄 요약

지금 구독은 `users.plan`+`plan_renews_at`의 **선불 기간권**(`activatePlan`)뿐이고 **자동 재청구가 없다**. 빌링키·스케줄러·상태머신이 전무한 **그린필드**다. 넷플릭스식(빌링키) 구조 5조각 — **①발급 → ②저장 → ③스케줄러 → ④월 리필 → ⑤상태머신(더닝)** — 을 `src/billing/portone.*`(eximbay 구조 미러) + 신규 3테이블 + off-by-default 스케줄러로 붙인다.

## 0.5 확정 사항 (2026-07-13 결정 세션)

**분담**: 결제 백엔드(빌링키·스케줄러·상태머신·PG 연동) = 개발자(eatapple1004). 가격 정합·프론트 표시·설계 문서 = 이 세션(Claude). 사용자 = PG/카드사 심사 통과 + 사업 결정.

**로케일·통화 모델(3축 독립)**: 지역 자동감지(IP)가 **언어·결제통화 기본값**만 세팅. 사용자는 언어(ko/en)와 결제통화(₩/$)를 **각각** 변경 가능. 화면 = 단일 통화(₩·$ 혼합 표시 금지), **표시통화 = 결제통화 = PG**. 첫 방문 지역감지는 기존 i18n(ko/en)에 얹음.

**통화 ↔ PG ↔ 능력 매트릭스**(사용자 확인):

| 기능 | ₩ KRW · 국내 (NHN KCP) | $ USD · 해외 (Eximbay) |
|------|:---:|:---:|
| 구독(정기결제/빌링키) | ✅ | ✅ (해외카드) |
| 크레딧 팩(일회성) | ✅ | ✅ |
| 국내카드 | ✅ | ⚠️ 일회성만(정기 ❌) |
| 해외카드 | ❌ (거부) | ✅ |

→ **구독은 카드 국적이 통화를 강제**: 국내카드=₩(KCP)만, 해외카드=$(Eximbay)만. 일회성은 교차 가능(국내카드로 $ 결제 OK). 카드는 입력 전 모름 → 지역으로 기본값 잡고, 불가 조합은 숨김/비활성 + 실패 시 안내.

**정기결제 = 2 프로바이더**: `portone`(KCP·₩ 국내) + `eximbay`(해외카드·$ 국외). §4 `subscriptions.provider`·스케줄러·상태머신·멱등 구조가 둘을 그대로 수용(스케줄러가 각 구독의 provider로 청구). **⚠️ 신규 작업**: Eximbay는 현재 일회성만 구현 → **해외 정기결제(빌링) 연동 추가** 필요(KCP 구독과 별개 트랙, 개발자).

**지역별 UI 차이**: 양쪽 다 구독 노출(구독 유무 분기 없음). 차이 = 통화·VAT표기·법적문구·언어. 국내="VAT 포함 · 매월 자동결제 · 언제든 해지 · 청약철회/사업자정보", 해외="$ · VAT excl. · Billed monthly".

**확정 가격(KRW, VAT 포함)** = USD × 1,503.60(2026-07-13) × 1.10 라운딩, 고정가 페그(실시간 변환 아님):

|------|-----|-----|---|-----|-----|-----|
| Starter | $19 | ₩31,000 | · | pack9 | $9 | ₩15,000 |
| Standard | $49 | ₩81,000 | · | pack49 | $49 | ₩81,000 |
| Pro | $99 | ₩164,000 | · | pack199 | $199 | ₩329,000 |

## 1. 현황(as-is) — 코드 실사

### 1.1 결제 PG (일회성 크레딧 팩만 존재)
| PG | 흐름 | 코드 | 상태 |
|----|------|------|------|
| **Eximbay** (USD) | `ready()` → fgkey → 팝업 → `status_url` 서버알림 → `/verify` 위변조검증 → 크레딧 충전 | `src/billing/eximbay.service.js`·`eximbay.route.js` | 키 미설정, 심사 막바지 |
| **LemonSqueezy** (USD) | `POST /checkout` → 결제페이지 → webhook `order_created`(HMAC-SHA256 서명검증) → 충전 | `src/billing/billing.route.js` | 폴백 보존, 키 미설정 |
| **PortOne+KCP** (KRW) | — | **없음** | **이번 작업** |

- 멱등 핵심 패턴: `payments(provider, order_id)` **UNIQUE** + `billing_orders`(redirect형 pending 추적). 이 패턴을 정기청구에 그대로 이식한다.
- 라우트 배선(`src/index.js`): webhook·status_url은 서명/원본바디 필요 → `express.raw`/`express.text`로 **`express.json`보다 먼저** 마운트(인증 없음). 나머지는 `requireAuth` 뒤.

### 1.2 구독 (선불 기간권 — 자동재청구 없음)
- `users.plan`(free|starter|standard|pro|premium) + `users.plan_renews_at`(만료일) + `pro_offer_started_at`(24h 오퍼).
- `subscription.service.activatePlan(userId, plan, nowMs, months=3)`:
  - months개월 부여 → `plan_renews_at`=만료일, **자동재청구 없음**.
  - 기간분 크레딧 **일괄** 지급(`monthlyCredits × months`, 누적).
  - 중복구매 정책: 상위=즉시 상향+기간 이어붙임, 하위=활성 중 차단(409).
  - **주석에 이미 "eximbay 정기결제 오픈 시 이 함수를 재청구 webhook에서 반복 호출(월 리필)로 재활용" 설계됨** → 우리는 이걸 1개월 리필로 재활용한다.
- `entitlements.planKey()`: `plan_renews_at`이 지나면 **자동으로 'free' 강등**(자동재청구 없이도 만료 반영). 정기결제는 이 만료일을 매달 갱신하는 것으로 귀결.
- `subscription.route.upgrade`: 일반 사용자는 `501 comingSoon`, admin만 `activatePlan`. → **여기를 실결제로 교체**.

### 1.3 크레딧 원장
- `credit.service.applyDelta`: 행 잠금(`FOR UPDATE`) + `credit_ledger(balance_after)` 원자 트랜잭션. `addCredits`/`charge`/환불. → 월 리필은 `addCredits`(type='plan') 재사용.

### 1.4 가격 정합 이슈(⚠️ 심사 블로커)
| 구분 | 소스 | 상품 |
|------|------|------|
| **표시가** | `pricing.config.js`·`public/js/pricing.js`(동일) | plans starter$19/standard$49/pro$99/premium$199 · packs pack9/49/199/349 (cr 3000~128000) |
| **결제엔진 실상품** | `billing.route.js` `PACKS` | pack50/120/300/700 ($5~56, cr 50~700) |

→ **ID조차 안 맞음**(표시가 pack9로 결제요청 시 엔진 "Unknown pack" 거절). 실결제는 100% USD. **원화 PG 심사 전 반드시 정합**(§9).

### 1.5 로컬/prod 격리 & 스케줄러 안전 선례
- `.env`(→`HeyHoAI-launch/.env`) = **prod RDS**, `PORT=3001`, `NODE_ENV=development`.
- :3002 = `DATABASE_URL=...doppia_local` 오버라이드로 기동(로컬 DB).
- **`DISABLE_VIDEO_POLLER=true` 패턴 존재**: "로컬 :3001이 prod DB에 붙으면 폴러가 prod 잡을 이중폴링" 방지용 off 스위치. → **정기청구 스케줄러도 동일하게 off-by-default**로 설계(§6, §10). 이게 이 작업의 최대 안전장치.
- 스케줄러 인프라 없음(cron 라이브러리 미설치, `setInterval`만 사용) → 경량 티커로 시작.

## 2. 착수 전 결정 3건 (추천 포함)

### 결정 A — PortOne API 버전: **V2 추천**
| | V1 (아임포트, `customer_uid`) | **V2 (신규 표준)** |
|---|---|---|
| 인증 | `/users/getToken`(imp_key/secret) | `Authorization: PortOne <API_SECRET>` (토큰 불필요) |
| 발급 | SDK `IMP.request_pay({customer_uid})` | SDK `PortOne.requestIssueBillingKey({channelKey})` |
| 청구 | `POST /subscribe/payments/again` | `POST /payments/{paymentId}/billing-key` |
| PG측 예약 | `/subscribe/payments/schedule` 내장 | `POST /payments/{paymentId}/schedule` |
| 웹훅 검증 | 수동 | `@portone/server-sdk` `Webhook.verify` |
| 멀티PG | customer_uid | `channelKey`로 KCP 라우팅(추상화) |

- **추천 = V2**: 그린필드 신규 연동 표준, 서버 SDK 웹훅 검증 내장, KCP를 `channelKey`로 추상화(추후 타 PG 확장 용이), REST가 우리 eximbay 패턴과 더 잘 맞음.
- **⚠️ 대시보드 확인 필요**: PG 채널(KCP 빌링)이 **어느 콘솔에 등록됐는지**. 일부 KCP 계약은 V1(아임포트) 콘솔 전용일 수 있음. V2 콘솔에 KCP **빌링(정기)** 채널이 있으면 V2 확정.
- 이 결정이 **전체 코드 모양**(SDK 함수·API 엔드포인트·인증·웹훅)을 좌우 → 착수 전 필수.

### 결정 B — 분담: 내가 직접 vs 개발자(eatapple1004)
- 결제는 민감(실카드·실청구) → 소유·검증 책임을 먼저 확정. 선택지 §초안:
  - **(a)** 스키마+서비스+스케줄러+상태머신 골격을 내가 :3002에서 구현·E2E → 개발자가 리뷰+prod migrate/키설정/스케줄러 on/push (권장: 속도+안전 분리).
  - **(b)** 설계만 확정하고 결제 코드 전체를 개발자가 구현.
  - **(c)** 완전 공동(hot 영역 분담, worktree 격리).

### 결정 C — KRW 가격 티어 + 정합 방향
- 현재 KRW 상품 전무. **월 KRW 티어 확정 필요**(§9 placeholder 제안). 동시에 표시가↔엔진 packs 정합(§9)은 정기결제 착수 전 마일스톤 0으로 처리 권장.

## 3. 타깃 아키텍처(to-be) — 넷플릭스식 빌링키

```
[사용자]                [프론트 PortOne SDK]        [우리 백엔드]              [PortOne/KCP]
  카드 1회 인증 ───────▶ requestIssueBillingKey ───▶                            ─▶ 빌링키(토큰) 발급
                              (billingKey 수신) ────▶ POST /portone/issue ─────────────┐
                                                      billing_keys 저장(토큰만)          │ 카드번호는 PG 보관
                                                      subscriptions 생성(next_charge_at) │ (우리는 last4만)
                                                                                         
  ── 매달(자동) ──────────────────────────────────▶ [스케줄러 티커]
                                                      due 큐(next_charge_at<=now)
                                                      → charge(paymentId 멱등)  ────────▶ POST /payments/{id}/billing-key
                                                      ← 성공: 월 리필 + 기간전진             ← 승인/실패
                                                      ← 실패: 상태머신(재시도→유예→강등)
                                                     ↕ webhook(서명검증) 이중확인 ◀──────── 결제 상태 알림
```

**붙일 5조각**
1. **발급** — 프론트 PortOne SDK로 빌링키 발급 → 백엔드 저장 엔드포인트.
2. **저장** — `billing_keys`(토큰) + `subscriptions`(plan·next_charge_at·status).
3. **스케줄러** — 일 1회 KST 티커, `next_charge_at<=now` 큐를 멱등 청구. **off-by-default**.
4. **월 리필** — 청구 성공 시 `activatePlan` 재활용(1개월분 크레딧 + `plan_renews_at` 갱신).
5. **상태머신** — 연체 재시도 → 유예 → free 강등 / 취소=빌링키 삭제 / 플랜변경 일할.

## 4. 데이터 모델 (신규 3테이블 · migrate.js 멱등 추가)

기존 `payments`/`billing_orders`는 USD 일회성 전용이라 건드리지 않고 분리한다.

```sql
-- ① 빌링키(재사용 토큰) — 카드번호 없음. PG가 카드 보관.
CREATE TABLE IF NOT EXISTS billing_keys (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id     UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    provider    VARCHAR(30) NOT NULL DEFAULT 'portone',   -- portone(kcp)
    billing_key TEXT NOT NULL,                            -- PG 발급 토큰(민감치 아님, but 비공개)
    channel     VARCHAR(60),                              -- KCP 빌링 channelKey
    card_brand  VARCHAR(30),                              -- 표시용(신한/삼성…)
    card_last4  VARCHAR(4),                               -- 표시용
    status      VARCHAR(20) NOT NULL DEFAULT 'active',    -- active | deleted
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE(provider, billing_key)
);
CREATE INDEX IF NOT EXISTS idx_billing_keys_user ON billing_keys(user_id) WHERE status='active';

-- ② 구독 인스턴스 — 정기청구의 주체. next_charge_at = 스케줄러 큐.
CREATE TABLE IF NOT EXISTS subscriptions (
    id             UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id        UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    plan           VARCHAR(20) NOT NULL,                  -- starter|standard|pro|premium
    status         VARCHAR(20) NOT NULL DEFAULT 'active', -- active|past_due|grace|canceled|expired
    provider       VARCHAR(30) NOT NULL DEFAULT 'portone',
    billing_key_id UUID REFERENCES billing_keys(id) ON DELETE SET NULL,
    currency       VARCHAR(3)  NOT NULL DEFAULT 'KRW',
    amount         INT NOT NULL,                          -- KRW 정수(무소수). 서버권위값.
    interval       VARCHAR(10) NOT NULL DEFAULT 'month',  -- month | year
    current_period_start TIMESTAMPTZ NOT NULL DEFAULT now(),
    current_period_end   TIMESTAMPTZ NOT NULL,            -- = users.plan_renews_at 미러
    next_charge_at       TIMESTAMPTZ,                     -- KST 기준 계산해 UTC 저장. null=청구정지
    retry_count    INT NOT NULL DEFAULT 0,
    cancel_at_period_end BOOLEAN NOT NULL DEFAULT false,
    canceled_at    TIMESTAMPTZ,
    created_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at     TIMESTAMPTZ NOT NULL DEFAULT now()
);
-- 활성 구독 1인 1개 강제(중복 정기청구 방지)
CREATE UNIQUE INDEX IF NOT EXISTS uq_sub_user_active
    ON subscriptions(user_id) WHERE status IN ('active','past_due','grace');
-- 스케줄러 due 큐 인덱스
CREATE INDEX IF NOT EXISTS idx_sub_due
    ON subscriptions(next_charge_at) WHERE status IN ('active','past_due');

-- ③ 청구 시도 이력 — 멱등 + 감사. paymentId 결정적 생성이 이중청구 방지의 핵심.
CREATE TABLE IF NOT EXISTS subscription_charges (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    subscription_id UUID NOT NULL REFERENCES subscriptions(id) ON DELETE CASCADE,
    user_id         UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    provider        VARCHAR(30) NOT NULL DEFAULT 'portone',
    payment_id      TEXT NOT NULL,        -- 멱등키 = sub_{subId}_{YYYYMM} (기간당 결정적)
    billing_key     TEXT,
    amount          INT NOT NULL,
    currency        VARCHAR(3) NOT NULL DEFAULT 'KRW',
    status          VARCHAR(20) NOT NULL DEFAULT 'pending', -- pending|paid|failed
    attempt         INT NOT NULL DEFAULT 1,
    pg_tx_id        TEXT,                 -- PortOne 거래 ID
    credits_granted INT,
    fail_reason     TEXT,
    raw             JSONB DEFAULT '{}',
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE(provider, payment_id)          -- 스케줄러 재실행·웹훅 중복 안전
);
CREATE INDEX IF NOT EXISTS idx_sub_charges_sub ON subscription_charges(subscription_id, created_at DESC);
```

**멱등 설계 핵심**: `payment_id = sub_{subscription_id}_{YYYYMM}`(기간당 결정적). 스케줄러가 겹쳐 돌거나 웹훅이 재전송돼도 (a) 우리 `UNIQUE(provider, payment_id)` (b) PortOne이 동일 paymentId 재사용 거절 — **이중 방어**. 기존 `payments(provider, order_id)` 패턴과 동형.

`users` 변경: **없음**(plan/plan_renews_at 재사용). 구독 상태는 `subscriptions.status`가 소스오브트루스, entitlement는 여전히 `plan_renews_at` 만료로 판정(planKey 무변경).

## 6. 정기청구 스케줄러 (KST · 멱등 · off-by-default)

```
[티커] 매 N분(예 10분) 또는 일 1회 03:00 KST
  1. SELECT ... FROM subscriptions
     WHERE next_charge_at <= now() AND status IN ('active','past_due')
     ORDER BY next_charge_at
     FOR UPDATE SKIP LOCKED LIMIT 50            -- 멀티인스턴스/겹침 안전
  2. for each due sub:
     a. paymentId = sub_{id}_{period YYYYMM}
     b. INSERT subscription_charges(pending) ON CONFLICT(provider,payment_id) DO NOTHING
        → rowCount==0 이면 이미 처리 → skip (멱등)
     c. POST /payments/{paymentId}/billing-key  { billingKey, amount, currency:'KRW', orderName }
     d. 성공 → §7 advance() : charge=paid, 월 리필(§8), 기간전진, retry_count=0
        실패 → §7 dunning() : 재시도 스케줄 / past_due / grace / 강등
  3. 웹훅이 오면 동일 paymentId로 상태 재확인(스케줄러 결과와 이중확인)
```

- **환경 스위치**: `BILLING_SCHEDULER_ENABLED`(기본 `false`) — `DISABLE_VIDEO_POLLER` 패턴 미러. `index.js`에서 `env.BILLING_SCHEDULER_ENABLED && startBillingScheduler()`.
- **prod 오접속 가드**(하드 제약): `DATABASE_URL`이 prod 호스트(`heyhoai.cluster-...rds`)를 포함하면 스케줄러가 `BILLING_SCHEDULER_PROD_OK !== 'true'`일 때 **기동 거부**(harness 스크립트의 doppia_local 가드와 동형). → :3001/로컬에서 실카드 청구 원천 차단.
- 시간대: 서버 UTC 가정. `next_charge_at`은 KST 기준(가입일 앵커)으로 계산해 UTC로 저장. cron 라이브러리 없이 `setInterval` 티커 + DB 시각 비교로 시작(라이브러리 추가 지양).
- 단일 인스턴스(`ecosystem instances:1`)라 경합은 낮으나, `SKIP LOCKED`로 미래 스케일아웃 안전.

## 7. 상태머신 (더닝 — dunning)

```
                 ┌────────── charge 성공 ──────────┐
                 ▼                                  │
  active ──charge실패──▶ past_due ──재시도성공──▶ active(기간전진, retry=0)
   ▲                        │
   │                        ├─ retry<3 : next_charge_at += [1d,3d,5d], retry++
   │                        └─ retry>=3: grace (current_period_end까지 권한유지 + 짧은 유예 D+3)
   │                                        │
   │                                        ├─ 유예중 결제성공 ──▶ active
   │                                        └─ 유예만료 ──▶ expired : plan_renews_at=now → planKey가 free 강등
   │
 사용자 취소 ─┬─ 기말해지 : cancel_at_period_end=true, next_charge_at=null → 기말 expired
             └─ 즉시해지 : PG 빌링키 DELETE + status=canceled + (정책상 잔여기간 유지 or 일할환불)
 플랜변경 ────┬─ 업그레이드 : 즉시 일할차액 청구 + plan 상향 + 다음 amount 갱신
             └─ 다운그레이드: current_period_end에 적용(기말)
```

- **강등은 코드 무변경 재사용**: `expired` 시 `plan_renews_at`을 과거로 → 기존 `planKey()`가 자동 free 처리. 별도 강등 로직 불필요.
- 재시도 간격·유예일·즉시해지 환불 여부는 §13 열린 질문(정책 확정 필요).

## 8. 월 리필 (activatePlan 재활용)

- 신규 `subscription.service.refillForPeriod(userId, plan)`:
  - `addCredits(userId, PLANS[plan].monthlyCredits, {type:'plan', description:'{plan} 월 구독 리필'})`
  - `UPDATE users SET plan=$plan, plan_renews_at=current_period_end`
- 즉 `activatePlan(months=1)`의 크레딧+갱신 부분만 떼어 재청구마다 호출. 주석에 예고된 "재청구 webhook에서 월 리필로 재활용"의 실체.
- **정책 결정(§13)**: 월 크레딧 **리셋 vs 누적**. 현행 `activatePlan`은 누적(add). 구독은 보통 "매월 리필" — 누적(add) 유지 제안(미사용분 이월), 또는 기간마다 리셋.

## 9. 가격 정합 방향 (마일스톤 0 — 정기결제 착수 전)

1. **packs 단일소스화**: `billing.route.PACKS`(pack50/120/300/700)를 폐기하고 `pricing.config.packs`(pack9/49/199/349 + cr/bonus)에서 파생 → 표시가=결제상품 ID/크레딧/가격 **완전일치**. (구독 서비스가 이미 `PRICING.plans`에서 가격 파생하는 것과 동형.)
2. **KRW 필드 추가**(✅ 확정·반영): `pricing.config` plans·packs에 `priceKRW` 추가.
   - starter ₩31,000 · standard ₩81,000 · pro ₩164,000 · premium ₩329,000 (월, USD×1,503.60×1.10 라운딩, VAT 포함). 상세 = §0.5 확정 가격표.
   - packs도 원화 병기(pack9 ₩15,000 …).
3. `subscriptions.amount` = `plan.priceKRW`(서버권위). 연간(`interval='year'`)은 `priceY×12` KRW.
4. `users.plan` 컬럼 주석의 옛 `creator/pro/brand` → 실제 `starter/standard/pro/premium`로 정합(문서/주석만).

  PORTONE_WEBHOOK_SECRET=      # 웹훅 서명검증
  BILLING_SCHEDULER_ENABLED=false     # 기본 off (DISABLE_VIDEO_POLLER 미러)

  ```

## 11. 테스트 계획 (:3002 로컬 DB 전용 — 하드 제약)

- 기동: `DATABASE_URL=postgresql://.../doppia_local PORT=3002 BILLING_SCHEDULER_ENABLED=true DISABLE_VIDEO_POLLER=true node --watch src/index.js`
- 로컬 DB migrate(신규 3테이블 멱등 반영).
- PortOne **테스트 채널**(KCP 테스트 MID) + 테스트 카드로 빌링키 발급.
- E2E 시나리오:
  1. **발급→구독개시**: billing-key 저장 + subscriptions 생성 + 첫 청구 paid + 크레딧 지급 + plan_renews_at 설정.
  2. **정기청구**: `next_charge_at`을 과거로 세팅 → 티커 1회 → charge=paid·월 리필·기간전진·retry=0 단언.
  3. **멱등**: 티커 2회 연속 → subscription_charges 1행만(UNIQUE payment_id) 단언.
  4. **실패→더닝**: 테스트 거절카드 → past_due + 재시도 스케줄 단언 → 유예 → expired 시 planKey free 단언.
  5. **취소**: 기말해지=next_charge_at null + 기말 강등 / 즉시해지=PG 빌링키 DELETE 단언.
- **금지**: :3001(prod DB)에서 청구/스케줄러 기동 절대 금지. 실청구는 승인 후 prod에서만.
