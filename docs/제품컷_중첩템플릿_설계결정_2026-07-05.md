# 제품컷 · 중첩 템플릿 설계 결정 (2026-07-05)

> 새 오피셜 테마/템플릿 도입 + "템플릿 안 템플릿 / 테마 안 테마" 중첩 방향에 대한 결정 기록 및 새 세션 핸드오프.
> 결정자: 사용자(Chief). 정리: Claude 세션 714123b8.

---

## 1. 배경 · 레퍼런스

- 목표: **새 오피셜 테마·템플릿** 추가. 첫 대상 = **제품컷**(의류 이미지 1장 → 제품컷 생성).
- 컷 종류 5종: **바닥컷 · 옷걸이컷 · 고스트컷 · 오브제컷 · 디테일컷**.
- 레퍼런스(laongen.com/product-cut/create): `제품컷 유형(부모) → 효과(세부옵션) → 옵션 추가로 배치 누적 → 생성`.
  즉 "유형 선택 → 세부옵션 → 여러 컷 묶어 생성" 패턴.

## 2. 결정 (확정)

### 2-1. 중첩의 성격 = **파라미터형 (1 템플릿 + 세부옵션)**
- 컷 5종은 **테마도 아니고, 5개의 별도 템플릿도 아님** → **하나의 "제품컷" 템플릿의 세부옵션(파라미터)**.
- UX상: 업로드 1회 → 컷 유형 선택 → 생성 (laongen 구조 그대로).
- 데이터상: 컷마다 프롬프트 레시피가 다르므로(바닥컷 ≠ 고스트컷) → **컷별 자식 레시피를 품은 부모 템플릿**. 즉 "템플릿 속 템플릿"이 파라미터 UI 뒤에 숨는 형태. → 사용자가 처음 말한 "템플릿 안 템플릿"이 여기서 실현됨.

### 2-2. 컷 5종을 어디에 둘까 = **세부옵션(파라미터) 레벨** (테마 X, 5템플릿 X)
- **테마로 쪼개면 ❌**: 테마 필터가 5개로 불어나고 "제품컷 하나의 흐름"이 깨짐. 테마는 큰 탐색 축이라 컷 종류엔 과함.
- **템플릿 5개로 쪼개면 △**: 같은 입력(의류 이미지 1장)을 공유하는데 진입점이 5곳으로 흩어지고 유지보수 5배.
- **파라미터로 두면 ✅**: 진입점 1개 + 컷 유형 선택. 확장도 쉬움(아래 4장).

### 2-3. 권장 구조
```
대분류(macro_group): Shopping
 └ 테마(theme): "제품컷"            ← 탐색/분류 단위 (신규 오피셜 테마)
    └ 템플릿(template): "제품컷"     ← 진입점 1개 (신규 오피셜 템플릿 = 부모)
       ├ 세부옵션 축1 · 컷 유형: 바닥컷·옷걸이컷·고스트컷·오브제컷·디테일컷  ← 각각 자식 레시피
       └ 세부옵션 축2 · 효과(선택): 스튜디오·자연광·그림자 …
          → (컷 유형 × 효과) 조합마다 내부 레시피 매핑
```

### 2-4. 테마 중첩(테마 안 테마)은 **지금 안 함**
- 지금은 컷을 템플릿 파라미터로만. 테마 중첩은 **나중에 카탈로그가 커질 때** 별도 진행(예: Shopping › 의류 › 제품컷/착용컷/룩북…).
- 이유: 테마는 현재 `vertical` 단일값 **flat 구조** → 계층화하려면 새 컬럼/테이블 필요(스키마 변경). 템플릿 중첩과 **분리된 작업**.

## 3. "추후 템플릿 중첩 추가 가능한가?" → **예 (스키마 변경 없이)**

현재 코드 스키마 스캔 결과(구현 시 정확한 라인·배선 재확인 필요):

- **레시피 테이블 `config`가 JSONB** → 컷별 참조(`config.parent_id`)와 오버라이드를 **데이터로** 넣을 수 있음. 컬럼 추가 불필요.
- **`recipeResolver.js`에 부모→자식 deep-merge 로직 존재** + **재귀** → 3단·4단 중첩도 코드 변경 없이 데이터만 추가하면 열림.
- **딱 하나 1회성 코드**: `recipe.route.js`의 `/api/recipes/:id/resolve`가 아직 부모를 조회해 `parentConfig`로 넘기지 않음 → **약 10줄** 부모 조회 로직 1회 추가하면 상속 활성화. 그 뒤로는 계속 데이터만으로 확장.
- ⚠️ 테마 중첩은 별개(위 2-4) — 스키마 필요.

## 4. 구현 로드맵 (새 세션)

**Phase 0 — 착수 전 확인 (필수)**
- `src/recipes/recipeResolver.js`(deepMerge·resolveRecipe), `recipe.route.js`(resolve 라우트), `recipeStore.js`(getById), `src/recipes/seeds/recipes.*.v2.js` 스키마, `public/js/themes.js`(CAT_THEMES) 실제로 열어 확인. (본 문서는 스캔 기반이라 라인·필드명은 재검증.)
- 시드 규칙/기록 루틴: `docs/섹션명령서/00_총지휘_종합관리.md` §7-6, `node scripts/consolidate_recipes.js`.

**Phase 1 — 데이터만 (스키마 변경 0)**
- 신규 오피셜 테마 "제품컷" 정의(themes.js CAT_THEMES에 Shopping vertical 추가 여부 검토 — 기존 vertical 재사용 or 신규 slug).
- 부모 템플릿 "제품컷" + 컷 5종 자식 레시피를 seed(`recipes.<section>.v2.js`)에 추가. 자식은 `config.parent_id: "제품컷"` + 컷별 프롬프트 오버라이드.
- `node scripts/consolidate_recipes.js`로 검증 → `_STATUS.md`·`_CATALOG.json` 갱신 + 백본 문서 동기화(CLAUDE.md 기록 루틴).

**Phase 2 — 1회 배선 (~10줄 코드)**
- `recipe.route.js` resolve: `recipe.config.parent_id` 있으면 부모 레시피 fetch → `resolveRecipe(config, { parentConfig, ... })`로 전달. (여러 단계면 부모 체인 순회.)
- ⚠️ 백엔드 변경 → 배포 시 pm2 restart.

**Phase 3 — Studio UI**
- 제품컷 템플릿 선택 시 세부옵션(컷 유형 그리드 + 효과) 노출 → 선택값을 resolve 요청에 반영. laongen식 "옵션 추가/배치" 채택 여부는 UI 결정.

**Phase 4 — 더 깊은 중첩 (미래, 코드 0)**
- 컷 안에 또 세부 = `parent_id` 체인만 데이터로 추가. resolver deep-merge 재귀가 처리.

## 5. 남은 결정거리 (구현 전 확정 필요)
- 효과(축2) 목록 확정 여부 — 축1(컷 유형)만 먼저 갈지, 효과까지 동시에 갈지.
- "제품컷" 테마를 신규 vertical slug로 만들지, 기존 fashion/general에 얹을지.
- laongen식 "옵션 누적 배치 생성"을 도입할지(부모 1클릭 = 여러 컷 동시), 아니면 단건 선택 생성인지. (원래 사용자 선택은 파라미터형=단건 변형이나, 배치 UX는 별도 얹기 가능.)
- 크레딧 과금: 컷 유형별 credit_cost 차등 여부.
