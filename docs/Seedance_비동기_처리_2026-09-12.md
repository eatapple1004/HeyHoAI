# Seedance 비동기 처리 — 문제·원인·해결

**작성일** 2026-09-12 · **환경** dev(doppia_dev) · **관련 PR** #338 #344 #347 #348 #349

## 1. 한 줄 요약

Seedance(fal.ai)는 **비동기 API**라 우리 서버가 죽어도 fal 쪽에서는 영상이 완성된다.
그런데 우리는 그 결과를 가리키는 **손잡이(request_id)를 메모리에만 들고 있어서**,
서버가 재시작되면 이미 비용을 지불한 렌더를 통째로 버린다.

## 2. 왜 비동기여야 하는가

동기(요청 하나로 끝까지 기다리기)로는 **구조적으로 불가능**하다.

| 제약 | 수치 | 출처 |
|---|---|---|
| Seedance 씬 1개 생성 시간 | **약 190초** (fast·4초·720p) | 실측 |
| UGC 1편(5컷) 총 소요 | **7~10분** (동시성 2) | 실측 |
| Cloudflare 프록시 타임아웃 | **100초** | 무료/Pro 플랜 고정값 |
| 브라우저·로드밸런서 타임아웃 | 통상 60~120초 | 일반 |

씬 하나도 100초를 넘기므로 **동기 요청은 시작하자마자 524로 끊긴다.**
그래서 fal은 큐 방식만 제공하고, 우리도 잡(job)을 만들어 백그라운드로 돌린 뒤
클라이언트가 상태를 폴링하는 구조를 쓴다. 비동기는 선택이 아니라 **유일한 선택지**다.

## 3. fal의 비동기 계약

```
POST /bytedance/seedance-2.0/fast/image-to-video
 → 200 { request_id, status_url, response_url }     ← 손잡이

GET  {status_url}   → IN_QUEUE / IN_PROGRESS / COMPLETED
GET  {response_url} → { video: { url, file_size }, seed }
```

**핵심**: 제출 순간 fal은 작업을 자기 큐에 넣는다. 이후 우리 서버의 생사와 **무관하게**
렌더가 진행되고 완성된다. 비용도 그 시점에 확정된다.

## 4. 문제 — 무엇이 잘못됐나

우리 UGC 파이프라인은 손잡이를 **지역 변수**로만 들고 있다.

```
submit → request_id 수신 → 지역 변수에 보관 → pollUntilDone 루프(메모리)
                                   ↑
                        프로세스 죽으면 여기서 증발
```

`ugc_jobs` 테이블 컬럼:

```
id, user_id, team_id, n_clips, charge_amount, result_idx, hashtags,
duration_sec, created_at, updated_at, script, scene_clips, caption,
output_type, product, concept, title, visibility, error, status,
subtitle_mode, result_url
```

**`request_id`를 저장할 자리가 없다.** `scene_clips`는 *완성된* 클립만 담는다.

결과:

1. 배포·크래시·OOM으로 프로세스가 재시작되면 폴링 루프가 사라진다
2. fal은 계속 만들어서 완성해 둔다 (**비용 발생 완료**)
3. 우리는 그 결과를 조회할 `request_id`가 없어 **영원히 되찾지 못한다**
4. 잡은 `processing`에 갇히고, 사용자는 스피너만 본다

## 5. 다른 경로는 이미 해결돼 있다

같은 코드베이스 안에 **정답이 두 개** 있다.

| 경로 | 손잡이 저장 | 재시작 생존 |
|---|---|---|
| 일반 릴스 (`video_jobs`) | `provider_job_id` **DB 저장** + `startPoller()`가 DB 기준 폴링 | ✅ |
| 콘텐츠팩 (`content_packs`) | 진행 상태 저장 + **resume**(남은 컷부터 재개) | ✅ |
| **UGC (`ugc_jobs`)** | **없음 — 메모리 전용** | ❌ |

UGC만 다단계라는 이유로 자체 오케스트레이션을 쓰면서 이 보호를 빠뜨렸다.

## 6. 해결 방안

### 단계 ① — 손잡이를 저장한다 (작고 즉시 효과)

제출 **직후** 씬별 핸들을 DB에 남긴다.

```json
{ "sceneN": 2, "engine": "seedance",
  "requestId": "01a09320-...",
  "statusUrl":  "https://queue.fal.run/.../status",
  "responseUrl":"https://queue.fal.run/..." }
```

- 이미 비용을 낸 렌더를 **버리지 않게** 된다
- 재시작 후에도 수동·자동으로 결과를 회수할 수 있다
- `status_url`을 그대로 저장하는 이유: fal의 경로 규칙이 바뀌어도 깨지지 않는다

### 단계 ② — 재개(resume)

부팅 시 `failed` 처리 대신, 저장된 핸들로 **폴링을 이어받아** 남은 파이프라인
(조립·TTS·자막)을 계속한다. 콘텐츠팩의 `resume` 패턴을 그대로 따른다.
→ 오늘 같은 사고에서 **영상이 그대로 완성**된다.

### 임시 방어선 (이미 적용됨)

재개가 없는 동안 잡이 영구히 갇히지 않도록 회수기를 고쳤다.

- **회수기 게이트 분리** (PR #344): 회수기가 비디오 폴러와 같은 블록에 묶여 있어
  dev(`DISABLE_VIDEO_POLLER=true`)에서는 **한 번도 돌지 않았다**. 폴러는 "살아있는 잡 진행",
  회수기는 "죽은 잡 정리+환불"로 역할이 달라 분리했다.
- **판단 기준 교정** (PR #349): "2분 이상 묵은 잡"만 회수하던 것을 **부팅 시각 기준**으로 바꿨다.
  시작 40초 만에 죽은 잡은 부팅 시점에 나이가 2분 미만이라 건너뛰어졌고, 회수기가 부팅 1회만
  돌아 영원히 갇혔다. `pm2 instances:1 + fork`라 "새 프로세스가 떴다 = 이전 파이프라인 사망"이
  확정이므로 나이는 애초에 틀린 기준이었다.

⚠️ 회수기는 **잡을 닫고 환불할 뿐, 이미 만들어진 영상을 되찾지는 못한다.** 근본 해결은 ①②다.

## 7. 운영 수칙

- **렌더 진행 중 배포 금지.** 배포 전 `SELECT count(*) FROM ugc_jobs WHERE status='processing'` 확인
- 재개(②) 적용 전까지 이 수칙이 유일한 방어다

## 8. 참고 — 함께 발견된 별건 버그

`nanoBanana`가 이미지 URL을 `file://` 형태로 돌려주는데 공용 경로 변환기
(`servedPath.toLocalPath`)가 그 스킴을 못 풀어, **UGC 안에서 Seedance가 한 번도 성공한 적이
없었다**(PR #348). Kling은 다른 경로라 멀쩡해서 증상이 "Seedance 씬만 조용히 실패"로 나타났다.
해당 파일 주석은 이미 *"각자 판단하다 같은 버그를 세 번 냈다"*고 적고 있었고, 이번이 네 번째 변종이다.
